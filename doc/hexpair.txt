1. Introduction                                         *hexpair-introduction*

hexpair turns the current buffer into a hex view of ONE PAGE of its content
- an xxd dump with 'filetype' set to xxd (standard syntax highlighting) and
ABSOLUTE file offsets, bracketed by a banner saying which page it is.  A
file smaller than a page simply has exactly one.  |:HexPairOpen| does the
same for a file that is not loaded at all, reading only the page it shows,
so a file of any size opens instantly.

While hex mode is active, the byte under the cursor is highlighted in BOTH
columns of the dump: placing the cursor on a hex byte highlights the
corresponding ASCII character, and placing it on an ASCII character
highlights the corresponding pair of hex digits.

                                                        *hexpair-visual*
The same holds for a |Visual| selection: Vim highlights what you selected,
and hexpair highlights the same BYTES on the other side of the dump, so a
run of hex digits shows which text it is and a run of text shows which
bytes it is.  Characterwise, linewise and blockwise selections all work,
and a selection spanning several lines is mirrored line by line.  Only the
part on screen is mirrored - what is scrolled away cannot be looked at
anyway, and it keeps the work per cursor movement the same however much of
a page is selected.  Banner lines contribute nothing, as everywhere else.

Requires the `xxd` utility, which ships with Vim.  It is looked up on
$PATH first and then in the Vim runtime directory ($VIMRUNTIME), so on
Windows the bundled xxd.exe is found even when it is not on PATH.  No
other external tools are needed.

2. Usage                                                       *hexpair-usage*

Preferably open the file in binary mode: >

    vim -b file.bin
<
If the file was opened WITHOUT -b, the plugin re-reads it with `:edit ++bin`
on the first toggle to obtain the exact on-disk bytes (read-time conversions
such as CR stripping for fileformat=dos cannot be undone otherwise).

                                                        *hexpair-states*
A buffer hexpair has touched is in one of two views, and |:HexPairToggle|
moves between them:

HEX PAGE VIEW     the page as an xxd dump: offset column, hex column,
                  ASCII column, between the two banner lines.
WINDOWED TEXT     the same page's raw bytes as text, between the same two
                  banner lines.  Useful for reading strings, or for
                  pasting bytes in as text.

A buffer that TOGGLED from a plain buffer has a way back: |:HexPairUnhex|
re-opens the whole file as the ordinary, unpaged, non-binary view it was
before, with the 'binary', 'fileencoding', 'fileformat' and the other
options it had then, and the cursor where it was.

A buffer OPENED as hex (|:HexPairOpen|, vimhex) has no plain buffer to go
back to - it may have had no text view at all, and its file may be far too
large to load for the purpose - so |:HexPairUnhex| refuses it and names the
file to |:edit| instead.  In neither case would a plain |:w| help: once a
buffer holds one page instead of the whole file, showing it as the file
again would be a lie, and a plain |:w| would truncate the file down to that
page.

                                                        *hexpair-page-source*
Where the pages come from depends on what the buffer was when hex mode was
entered:

- UNMODIFIED AND BACKED BY A FILE - the usual case.  The file is the
  truth, so pages are read from it.
- NO FILE AT ALL, e.g. `cat data | vim -`.  The only copy of the content
  is in memory, so it is written once to a private temporary file and
  paged from there.  A plain |:w| has nothing to write back to and says
  so; `:w {file}` saves all of it and the view then goes on editing that
  file (see |hexpair-paged-write|).
  Pipe binary data in with `vim -b -`: without -b Vim may transcode it
  or fold its line endings on the way in, and unlike a named file there
  is nothing to re-read with ++bin afterwards.  hexpair warns when it
  pages a buffer that was not read in binary mode.
- MODIFIED AND BACKED BY A FILE.  The buffer and the file disagree, and
  hexpair refuses rather than choose for you: paging the file would hide
  your edits, and paging the buffer would let a page-range write drop
  every edit outside the visible page.  Write the buffer first, or use
  |:HexPairOpen| to look at what is on disk.

Only the HEX column matters when converting back: the offset column and the
ASCII column are stripped before the reverse conversion and are therefore
purely decorative.  This means you can freely insert, delete or reorder
lines while editing - inserted lines need no offset and no ASCII part, just
hex pairs.  After |:w| the page is re-read, so offsets and the ASCII column
become correct again automatically.  The banner lines contribute no bytes:
in the dump they are recognized by their leading double quote, and in the
windowed text view - where a page of raw bytes may itself start with one -
by matching the banner text exactly.

Editing rules:
- keep bytes in the hex area separated by at most ONE space; a run of two
  spaces marks the start of the (ignored) ASCII column,
- always write full byte pairs (an odd number of hex digits shifts all
  following bytes by a nibble).

Violations are refused, not guessed: a character in the hex area that is
not a hex digit makes both |:w| and toggling hex mode off fail with an
error, with the cursor parked on the offender - the dump and the file on
disk keep their previous content.  An odd TOTAL number of hex digits
(the last nibble would be dropped silently) is refused the same way.

Reloading the file with |:e| (or discarding dump edits with :e!) while
hex mode is active is safe: the freshly read content is converted to a
new dump, hex mode stays active and the cursor stays on the same byte
offset (best-effort after :e! discarded an edited dump).

The cursor position is preserved across toggling as a BYTE OFFSET: the
byte the cursor was on in the normal view is the byte it lands on in the
HEX column of the dump, and vice versa.  For a multibyte character this is
the offset of its first byte in the file encoding.  The same mechanism
keeps the cursor on the same byte across |:w| in hex mode, even when the
regenerated dump shifts all offsets because bytes were inserted or deleted.

For a buffer opened without -b the cursor is mapped around the ++bin
reload in two phases: the line and the within-line file-byte column are
captured from the converted view (with BOM and single-byte fileencoding
transcoding accounted for), and the line-start offset is then anchored
with line2byte() over the raw bytes - exact by construction regardless of
line endings, including files with mixed CRLF/LF.  Multibyte
fileencodings other than utf-8 (e.g. utf-16) do not preserve line
boundaries across the reload and remain approximate; the same applies to
the non-reloadable fallback (modified or unnamed buffers).

While editing the dump, the byte offset of the cursor is derived from the
hex pairs actually present before it, so after inserting bytes (on a bare
line or into an existing line) a |:w| keeps the cursor on the newly added
byte it was on, even though the regenerated dump reflows all lines.

Toggle hex mode with the mapping (|hexpair-mappings|) or the command:

                                                              *:HexPairToggle*
:HexPairToggle          Toggle between the normal buffer content and the
                        hex dump view.  The same command switches back.

                                                              *:HexPairUnhex*
:HexPairUnhex[!]        The way out for a buffer that toggled from a plain
                        buffer (|:HexPairToggle|): re-open the whole file as
                        the ordinary, unpaged, non-binary view it was before
                        - the bytes from the file, the 'binary',
                        'fileencoding', 'fileformat' and the other options
                        it had then, the cursor where it was.  The buffer is
                        re-read, not converted: a page is not the file.
                        ! discards unwritten edits to the page; without !
                        the command refuses, because a plain |:edit| would
                        otherwise lose them without a word.
                        A buffer opened as hex (|:HexPairOpen|, vimhex) has
                        no plain view to return to, so the command refuses
                        and names the file to |:edit| instead.  So does a
                        view paged from content with no file of its own
                        (piped in), and one whose file has changed on disk
                        since the page was read - reload the page
                        (|:HexPairPageGoto|!) and try again.
                        The file re-opened is the one the buffer holds when
                        the command runs, which after a |:saveas| is the
                        file it was saved as, not the one it was toggled
                        from.
                        `hexpair.vimrc` puts the bare command on `<Leader>u`
                        and the discarding one on `<Leader>U`, which is the
                        same lowercase/capital pair every other force
                        variant there uses.

                              *:HexPairGoHex* *:HexPairGoAscii* *:HexPairSwap*
:HexPairGoHex           Move the cursor to the HEX column, staying on the
                        same byte.
:HexPairGoAscii         Move the cursor to the ASCII column, staying on the
                        same byte.
:HexPairSwap            Move the cursor to the opposite column, staying on
                        the same byte.

The jump commands clamp to a sensible target: from the offset column they
land on the first byte of the line, from beyond the ASCII column on the
last byte, and on a short last line on its last existing byte.

:HexPairRefresh         Regenerate the offset and ASCII columns from the
                        current hex payload, without writing to disk; see
                        |hexpair-refresh|, where the command is described
                        in full.

                                        *:HexPairInspect* *HexPairInspect*
:HexPairInspect[!]      Read the bytes at the cursor as the numbers they
                        could be - 8, 16, 32 and 64 bits wide, unsigned
                        and signed, little- and big-endian, plus the two
                        IEEE 754 floats: >

    hexpair: byte 66 (0x42) of 512: 41 42 43 44 45 46 47 48
      8-bit    65                          char 'A'  bin 01000001  oct 0101
               little-endian               big-endian
      16-bit   16961                       16706
      32-bit   1145258561                  1094861636
      64-bit   5208208757389214273         4702394921427289928
      float32  781.035217                  12.141422
      float64  1.58398e40                  2393736.541207
      utf-8    U+0041 'A' (1 byte)
      utf-16   U+4241 '䉁' (2 bytes)       U+4142 '䅂' (2 bytes)
      utf-32   U+44434241 - past U+10FFFF  U+41424344 - past U+10FFFF
      block    Basic Latin
<
                        A |:HexPairInspect| on an ESC, at the start of a
                        UTF-16LE file, would end: >

      utf-8    U+001B (1 byte)
      utf-16   U+FE1B (2 bytes)            U+1BFF (2 bytes)
      utf-32   U+41FE1B - past U+10FFFF    U+1BFFFE41 - past U+10FFFF
      name     ESC (escape), a C0 control
      bom      utf-16le byte order mark
<
                        The signed reading follows the unsigned one where
                        the two differ ("43981 / -21555"), which is
                        exactly when the top bit is set.

                                                *hexpair-inspect-naming*
                        The last rows say what the character IS, and they
                        describe the UTF-8 reading: it is the one with no
                        byte order to choose, and naming all four readings
                        would be four lines of mostly noise.

                        "name" appears for a code point you cannot see -
                        every C0 and C1 control, DEL, and the space and
                        format characters a hex editor meets constantly
                        (NBSP, SOFT HYPHEN, the zero-width joiners and
                        the bidi marks).  "block" is the Unicode block,
                        which is the "what script even is this" question,
                        and is there for every code point that decodes -
                        with one exception: the byte order mark is named
                        but gets no block row.  U+FEFF is assigned to
                        "Arabic Presentation Forms-B" only because
                        Unicode lays out blocks by contiguity and FE70..
                        FEFF is the range that happens to close the BMP;
                        it is a format character that belongs to no
                        script, so a block row would only add a script
                        where there is none.
                        "bom" appears when the bytes at the cursor are a
                        byte order mark in any encoding - the one thing
                        the UTF-8 rows above cannot say, since ff fe is
                        not UTF-8 at all.

                        There is deliberately no full character NAME, the
                        LATIN SMALL LETTER E WITH ACUTE kind.  That needs
                        UnicodeData.txt, two megabytes of names for a
                        hundred and fifty thousand characters, which is a
                        different order of thing from a table of ranges
                        and does not belong inside a Vim plugin.  The
                        block table is Unicode 16.0.0, derived from the
                        Unicode Character Database under the Unicode
                        License V3; see NOTICE.md, which ships with the
                        plugin and carries that license in full.

                                                *hexpair-inspect-anywhere*
                        This command works in an ORDINARY buffer too, with
                        no hex view and no |:HexPairToggle| anywhere near
                        it: what is this character, is that a NBSP, does
                        this file start with a BOM.  The report is the
                        same, with two differences that matter.

                        The bytes are VIM's, not the file's.  A paged view
                        holds what is on disk because hexpair opened it
                        |++bin|; an ordinary buffer holds what Vim read it
                        into.  A file read as latin1 into a UTF-8 Vim is
                        latin1 on disk and UTF-8 in memory, and a
                        'fileformat' of "dos" has CRLF on disk and no CR
                        at all in the buffer.  A "note" row says so
                        whenever the two can differ - it is not there when
                        they cannot.

                        And nothing is marked on screen.  The marking is
                        drawn by the highlighting a paged buffer has and
                        an ordinary one does not, so `:HexPairInspect!`
                        has nothing to take off there and says as much.

                        The three text rows say what the bytes would be
                        as characters.  UTF-8 has no byte order to get
                        wrong; the other two are read each way round like
                        the numbers above them, and a UTF-16 high
                        surrogate takes the unit after it along.  Every
                        way an encoding can be wrong is its own answer
                        rather than a code point: an overlong UTF-8
                        sequence, a lone surrogate, a value past
                        U+10FFFF - none of those is a character, and a
                        data inspector that reported one for them would
                        be inventing it.

                        The character itself is shown next to its number
                        where there is one to show: not for a control
                        code, not for the private use areas (whatever
                        appears there means nothing without the font it
                        was meant to come with), and not at all unless
                        'encoding' is utf-8, since the message area would
                        not be reading those bytes as utf-8 either.

                        The bytes are THIS PAGE's, as the buffer holds
                        them - edits included - and stop at its end, so
                        near the boundary there may be fewer than eight
                        and the wider rows say how many are left rather
                        than reaching into a page that is not on screen.
                        Works in either view; a banner line has no byte
                        to read and says so.

                        Widths above 16 bits need a Vim whose |Number| is
                        64 bits (|+num64|) and the floats need |+float|;
                        without them those rows are left out rather than
                        shown wrong.

                        The bytes it read are marked on the page as well
                        (highlight group HexPairInspect, |Visual| by
                        default), in both columns, for as long as the
                        cursor stays on the byte they were read from.  The
                        report's first line already says which bytes it is
                        about; the marking saves counting eight pairs of
                        digits back off a line of forty-eight.  Where the
                        report could only read three, three are marked -
                        a marking of eight would be saying something the
                        report does not.  The bang takes it off at once,
                        and g:hexpair_show_inspect = 0 never draws it.

                                            *:HexPairInsertChar* *hexpair-insert-char*
:HexPairInsertChar [++enc={encoding}] {text}
                        Put the bytes of {text} in at the cursor.  The
                        data inspector above says what the bytes at the
                        cursor would be as utf-8, utf-16 and utf-32; this
                        is the same reading backwards - it writes a
                        character in exactly those. >

    :HexPairInsertChar Š                  " c5 a0
    :HexPairInsertChar ++enc=utf-16le Š   " 60 01
    :HexPairInsertChar ++enc=utf-32be Š   " 00 00 01 60
    :HexPairInsertChar ++enc=cp1250 Š     " 8a, if this Vim's iconv knows it
<
                        The bytes go in BEFORE the byte under the cursor
                        and push the rest of the page along - the same
                        edit as typing them into the dump, so they are
                        marked as changed (|HexPairModified|), one |u|
                        takes the whole insert back, nothing reaches the
                        file until |:w| does, and the write that carries
                        it is the length-changing one, which says what it
                        will cost and asks.  The hex view only: the text
                        view has no columns to put bytes into.

                        Which encoding is meant is
                        g:hexpair_insert_encoding ('utf-8' unless you say
                        otherwise) - a file is in one encoding, so the
                        question is worth answering once.  ++enc=
                        overrules it for a single insert without changing
                        it back afterwards, the same way |++enc| does for
                        |:edit|.

                        utf-8, utf-16le, utf-16be, utf-32le, utf-32be,
                        latin1 and ascii are COMPUTED from the character's
                        code point.  That is not a preference: |iconv()|
                        answers with a |String|, a String cannot hold a
                        NUL, and 'A' in utf-16le is 41 00 - a converted
                        answer would end at the first of those.  Computing
                        them also means they do not depend on what the
                        machine's iconv was built with.

                        Any other name IS handed to iconv(), and then
                        converted back and compared: a conversion that
                        lost a byte does not survive the round trip.  A
                        name this Vim does not know is refused rather than
                        quietly written as utf-8 - iconv() answers a
                        conversion it cannot do by handing the text back
                        unchanged, which for ASCII in an ASCII-compatible
                        encoding is what success looks like too, so the
                        name is probed with a character no encoding spells
                        the way utf-8 does.

                        <Plug>(HexPairInsertChar) asks for the text, since
                        a bare mapping cannot carry one; what you type may
                        begin with ++enc= just as the command's argument
                        may.

                                                        *:HexPairSyncViews*
:HexPairSyncViews       Bring every scroll-bound view of a page onto the
                        byte this one is on: the page holding it, the byte
                        itself, and level.

                        Rarely needed, because a JUMP already does it: a
                        jump names a byte, a byte means the same thing in
                        every view of the file, and so |:HexPairGoOffset|,
                        the search landings, |:HexPairDiffNext| and the
                        rest take the bound views along - whether the byte
                        was a page away or two lines away.

                        What does not is moving the cursor by hand.
                        'scrollbind' promises that windows MOVE together,
                        not that they are on the same byte, and within a
                        page they navigate independently - which they are
                        meant to.  After a while that leaves them showing
                        the same lines and different bytes, with no way
                        back.  This is the way back.

                        It also only ever syncs movement made from the
                        moment each window was bound, so a window scrolled
                        before Vim's main loop has run is never synced at
                        all.  That is not a corner: `vimhexdiff` jumps to
                        the first difference from inside |VimEnter|, and
                        without this the left window went to it while the
                        right one stayed at the top of page 1.

                        Only bound views follow, and only those showing a
                        page.  One that has unwritten changes, or whose
                        file does not reach that far, stays where it is
                        and says so - as for a page turn
                        (|g:hexpair_bind_pages|).

                                                          *:HexPairSelection*
:HexPairSelection       Say how many bytes the |Visual| selection covers,
                        and which: >

    hexpair: 18 bytes selected, 1041-1058 (0x411-0x422) of 5000
    hexpair: 12 bytes selected in 3 lines (4 per line), 1041-1076
             (0x411-0x434) of 5000
<
                        Characterwise and linewise selections are one run
                        of bytes and are reported as a range; a blockwise
                        one is not, so it leads with the count and says
                        how many lines and how many per line.  The
                        positions are 1-based, like the page banner's, so
                        they can be typed straight into |:HexPairGoOffset|.

                        Banner lines contribute no bytes here either; a
                        selection of nothing else says so.  In the text
                        view a column is a byte, and a linewise selection
                        takes in the line break that ends each line -
                        which in a page of raw bytes is a byte like any
                        other.

                        From Normal mode it reports the selection made
                        last ('< and '>), which is also how the Visual
                        mapping works: |<Plug>(HexPairSelection)| leaves
                        Visual mode, and that is what sets the marks.

                        It puts the selection back afterwards, and then
                        waits for a key: Vim draws its own "-- VISUAL --"
                        over the message line the moment it is back in
                        Visual mode, so a report that did not wait would
                        be gone before it could be read.  Press <Enter>
                        (or any key) to carry on with the selection still
                        there.  From Normal mode nothing redraws over it,
                        so nothing waits.

                                                    *hexpair-marking-views*
Every byte-level marking - the bytes you have edited (|HexPairModified|),
the bytes that differ from the file being compared with (|HexPairDiff|),
the matches of the search (|HexPairFind-highlight|) and the byte a mark
(|HexPairMark-highlight|) - is drawn in BOTH views, and only over the lines on
screen.  A dump has three columns per byte and one for its character; a
page of text has one column per byte, and the line break that ends a line
is a byte of the page with no column of its own, so it is the one byte
that is never marked.

In the text view the comparing markings work on the bytes as that view
spells them, which has exactly one consequence worth knowing: Vim cannot
hold a NUL in a string and writes one as a line break, so a NUL replaced
by a line break at the same offset (or the other way round) is not marked
as changed.  Every other edit is, including one that changes the length.

Everything here is measured in BYTES, so a file of UTF-8 text or one with
CRLF line endings marks exactly the bytes that are meant: a CR is a byte
of the page like any other (not a line ending Vim owns - a paged buffer is
always 'fileformat' unix, so one line break is one byte wherever Vim
runs), and one byte of a multi-byte character is marked as one byte.  The
only thing a byte offset cannot do in the text view is put the CURSOR
inside a character: |:HexPairGoOffset| on the second byte of a two-byte
character lands on the character, and says so with the offset it reached.
The hex view has a column per byte and reaches every one of them.

What is MARKED is still the byte; what you SEE is the character it is
part of, because a character is one cell on screen and Vim colours cells.
The hex view shows which byte it was.

3. Mappings                                                 *hexpair-mappings*

                                                        *<Plug>(HexPairToggle)*
 *<Plug>(HexPairUnhex)*
 *<Plug>(HexPairGoHex)* *<Plug>(HexPairGoAscii)* *<Plug>(HexPairSwap)*
                                                       *<Plug>(HexPairRefresh)*
                            *<Plug>(HexPairGoOffset)* *<Plug>(HexPairGoOffsetForce)*
                                                          *<Plug>(HexPairPages)*
                                                     *<Plug>(HexPairSyncViews)*
                    *<Plug>(HexPairInspect)* *<Plug>(HexPairInsertChar)*
                                                      *<Plug>(HexPairSelection)*
                     *<Plug>(HexPairMark)* *<Plug>(HexPairMarkDelete)*
             *<Plug>(HexPairGoMark)* *<Plug>(HexPairGoMarkForce)*
                             *<Plug>(HexPairFind)* *<Plug>(HexPairFindText)*
                  *<Plug>(HexPairFindNext)* *<Plug>(HexPairFindPrev)*
                  *<Plug>(HexPairDiffNext)* *<Plug>(HexPairDiffPrev)*
                                                     *<Plug>(HexPairDiffShow)*
         *<Plug>(HexPairModifiedNext)* *<Plug>(HexPairModifiedPrev)*
                                                 *<Plug>(HexPairModifiedShow)*
                 *<Plug>(HexPairFindClear)* *<Plug>(HexPairDiffClear)*
                                                       *<Plug>(HexPairMarks)*
The plugin defines NO key mappings by default; it only provides the
commands above and <Plug> mappings.  Choose your own keys in your vimrc -
or source the set below, which ships with the plugin as `hexpair.vimrc`
(|hexpair-vimrc|).  Every command that takes no argument has a target,
and so do the three that need a name typed - they ask for it: >

    " Views
    nmap <Leader>h <Plug>(HexPairToggle)
    nmap <Leader>u <Plug>(HexPairUnhex)
    nmap <Leader>< <Plug>(HexPairGoHex)
    nmap <Leader>> <Plug>(HexPairGoAscii)
    nmap <Leader>- <Plug>(HexPairSwap)
    nmap <Leader>r <Plug>(HexPairRefresh)

    " Moving around the file
    nmap <Leader>j <Plug>(HexPairPageNext)
    nmap <Leader>k <Plug>(HexPairPagePrev)
    nmap <Leader>g <Plug>(HexPairPageGoto)
    nmap <Leader>b <Plug>(HexPairGoOffset)
    nmap <Leader>? <Plug>(HexPairPages)
    " Bring the other scroll-bound view onto the byte this one is on
    nmap <Leader>= <Plug>(HexPairSyncViews)

    " Reading the bytes
    nmap <Leader>i <Plug>(HexPairInspect)
    " ... and the same the other way round: a character, written in as bytes
    nmap <Leader>I <Plug>(HexPairInsertChar)
    nmap <Leader>s <Plug>(HexPairSelection)
    xmap <Leader>s <Plug>(HexPairSelection)
    " Marks - all four under one prefix, because single letters run out
    nmap <Leader>ml <Plug>(HexPairMarks)
    nmap <Leader>ms <Plug>(HexPairMark)
    nmap <Leader>md <Plug>(HexPairMarkDelete)
    nmap <Leader>mg <Plug>(HexPairGoMark)
    nmap <Leader>mG <Plug>(HexPairGoMarkForce)

    " Searching
    nmap <Leader>/ <Plug>(HexPairFind)
    nmap <Leader>t <Plug>(HexPairFindText)
    nmap <Leader>f <Plug>(HexPairFindNext)
    nmap <Leader>F <Plug>(HexPairFindPrev)

    " Walking your own edits
    nmap <Leader>e <Plug>(HexPairModifiedNext)
    nmap <Leader>E <Plug>(HexPairModifiedPrev)
    " What was here before I edited it - a byte, or a whole selection
    nmap <Leader>d <Plug>(HexPairModifiedShow)
    xmap <Leader>d <Plug>(HexPairModifiedShow)

    " Comparing with another file
    nmap <Leader>] <Plug>(HexPairDiffNext)
    nmap <Leader>[ <Plug>(HexPairDiffPrev)
    " What that file has here - a byte, or a whole Visual selection
    nmap <Leader>D <Plug>(HexPairDiffShow)
    xmap <Leader>D <Plug>(HexPairDiffShow)

    " Turning the markings off again
    nmap <Leader>c <Plug>(HexPairFindClear)
    nmap <Leader>C <Plug>(HexPairDiffClear)

    " The same, discarding unwritten changes without asking - as the !
    " commands do; handy for reading through a file rather than editing it
    nnoremap <silent> <Leader>J :HexPairPageNext!<CR>
    nnoremap <silent> <Leader>K :HexPairPagePrev!<CR>
    nnoremap <silent> <Leader>U :HexPairUnhex!<CR>
    nmap <Leader>G <Plug>(HexPairPageGotoForce)
    nmap <Leader>B <Plug>(HexPairGoOffsetForce)
<
|:HexPairOpen| takes a file name, so it has no <Plug> target - it is for
the command line or a shell wrapper (see |hexpair-paged| for one).

|<Plug>(HexPairPageGoto)| and |<Plug>(HexPairGoOffset)| prompt with
|input()| for the number a bare <Plug> target cannot carry: press the
key, type a page (a number, +N or -N to step, $ for the last, $-N for N
back from it) or a byte offset (decimal or 0x-prefixed, with the same
+N, -N, $ and $-N), Enter.  An empty answer cancels.

|<Plug>(HexPairSelection)| is the one target worth mapping in TWO modes:
in Visual mode it reports the selection you are making, in Normal mode
the one you made last.  Map it with both `xmap` and `nmap`, as above.
The Visual one puts the selection back when it is done - asking about a
selection from the `:` line is what ends it, and losing it to look at it
is not a trade worth making.

|<Plug>(HexPairGoMark)|, |<Plug>(HexPairFind)| and
|<Plug>(HexPairFindText)| prompt for what their commands take as an
argument, the way |<Plug>(HexPairPageGoto)| does: press the key, type a
mark name (completed as you type), a byte pattern or a string, Enter.
An empty answer cancels.  |<Plug>(HexPairGoMarkForce)| is the mark
prompt that discards unwritten changes, like |:HexPairGoMark|!.

Or map the commands directly: >

    nnoremap <silent> <Leader>h :HexPairToggle<CR>
<
About the two pieces used above:

|<Leader>| is a placeholder that expands to the value of the
"mapleader" variable at the moment a mapping is DEFINED - backslash by
default, so `nmap <Leader>h ...` means `\h` out of the box.  To use a
different prefix, set the variable in your vimrc BEFORE the mappings
that use it: >

    let mapleader = ','       " comma as the prefix: ,h ,< ,> ,-
    nmap <Leader>h <Plug>(HexPairToggle)
<
Popular choices are comma and space (`let mapleader = ' '`); any other
non-conflicting prefix key works just as well.  See |mapleader|.

To inspect the effective value, use: >

    :echo string(get(g:, 'mapleader', '\'))
<
A plain `:echo mapleader` fails with E121 in the default setup: the
variable does not exist until you set it, Vim only falls back to
backslash internally.  The string() wrapper makes an invisible value
such as space visible.  Also note that because <Leader> is substituted
when a mapping is DEFINED, |:nmap| lists already-defined mappings under
their real keys (e.g. \h), not under <Leader>h.

|<Plug>| is a special key that can never be typed.  The plugin hangs
its functionality on <Plug>(HexPair...) targets and leaves the choice
of real keys entirely to you - that is why it defines no key mappings
of its own.  Mappings onto a <Plug> target must be created with |:nmap|,
NOT |:nnoremap|: the "nore" variants forbid the remapping through which
the <Plug> target expands, so the mapping would do nothing.

4. Configuration                                       *hexpair-configuration*

                                                    *g:hexpair_bytes_per_line*
g:hexpair_bytes_per_line
                        Number of bytes per dump line (xxd -c).  Default: 16.
                        Example for wide terminals: >
                            let g:hexpair_bytes_per_line = 32
<
                        Must be between 1 and 256, and
                        |g:hexpair_page_size| must be a multiple of it.
                        That range is the whole requirement: the width
                        itself divides nothing, and an odd one like 23 is
                        as good as 16.

                        256 is xxd's own ceiling (xxd.c: `#define COLS
                        256`), not a number chosen here; a larger -c
                        makes xxd exit with "invalid number of columns",
                        which would otherwise reach you as a command that
                        failed for reasons nothing connects to the
                        setting.  A zero is checked for by name rather
                        than caught by the multiple rule, because Vim
                        answers `512 % 0` with 0 rather than an error - so
                        a zero would otherwise pass that check and fail
                        later, in `xxd -c 0` and in every column sum on
                        the page.

                        Any width works everywhere, including past 2 GiB
                        on Windows (|hexpair-windows-2gib|): xxd is told
                        `-c N` there as anywhere else, and the offset
                        column that has to be renumbered in Vim advances
                        by N a line.
                                                             *g:hexpair_paste*
g:hexpair_paste         The 'paste' option is global, so it cannot be set
                        just for the dump buffer.  When this option is 1
                        (the default), the plugin switches 'paste' on
                        whenever the cursor enters a hex-mode buffer and
                        restores its previous value whenever the cursor
                        leaves it or hex mode is toggled off.  Insert-mode
                        mappings and abbreviations are then disabled in the
                        dump (they could mangle typed hex), and no automatic
                        indenting or formatting interferes; all other
                        buffers keep the user's own 'paste' state.  The
                        buffer's 'expandtab' is preserved across the
                        switch (turning 'paste' on would otherwise reset
                        it); 'softtabstop' is forced to 0 by 'paste' by
                        design while it is active (see |'paste'|).  Set
                        to 0 to leave 'paste' alone: >
                            let g:hexpair_paste = 0
<
                                                             *g:hexpair_ruler*
g:hexpair_ruler         A ruler line between the top banner and the dump,
                        numbering the byte columns - two digits over each
                        hex byte, the low nibble over each ASCII
                        character.  Default: 0 (no ruler). >

    let g:hexpair_ruler = 1
<
                        gives >

  " hexpair: page 2/10  bytes 513-1024 of 5000  disk.img
  "         00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f  0123456789abcdef
  00000200: 00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f  ................
<
                        Like the banners, the line starts with a '"' and
                        therefore contributes no bytes: it is never
                        written, and editing it changes nothing.  It is
                        drawn for the layout of the page's FIRST line, so
                        on a page that straddles the 4 GiB offset-width
                        change it lines up with the narrower half.  A
                        page keeps the setting it was opened with; a
                        later change takes effect on the next page.

                        The text view has no ruler - there are no columns
                        to number in a page of raw bytes.

g:hexpair_show_marks    Whether the byte a mark stands on is underlined

                                                    *g:hexpair_show_modified*
g:hexpair_show_modified Whether the bytes that differ from the ones on
                        disk - what has been edited and not yet written -
                        are marked with |HexPairModified|.  Default: 1. >

    let g:hexpair_show_modified = 0
<
                        What it compares is the POSITION, not the edit
                        history: after an insertion every byte behind it
                        is marked, because those offsets really do hold
                        something else now.  Only the lines on screen are
                        compared, and only when the page changes or
                        scrolls.

                        It costs one copy of the page's bytes as hex -
                        256 KB for the default 128 KiB page - which is the
                        same read the freshness check already needed.

                                                     *g:hexpair_bind_pages*
g:hexpair_bind_pages    Whether a page turn in this window is passed on to
                        the windows that are scroll-bound to it.
                        Default: 1. >

    let g:hexpair_bind_pages = 0
<
                        'scrollbind' is Vim's own "these windows move
                        together", and a page turn is the one kind of
                        scrolling it cannot follow by itself: the bound
                        window keeps the page it had, and the two then
                        scroll in step through different parts of their
                        files.  `vimhexdiff` (|hexpair-vimhex|) is where
                        this shows: it binds the two windows precisely so
                        that they show the same bytes.

                        A bound window follows by BYTE, not by page
                        number - two views need not be paged the same way
                        - and its cursor lands on that byte, so the two
                        dumps line up rather than merely scroll together.
                        The scrolling is levelled again afterwards
                        (|:syncbind|), since 'scrollbind' otherwise keeps
                        following the offset the two windows had before
                        the page turn.
                        A window is left where it is, with a message
                        saying so, when following would mean discarding
                        unwritten changes, or when its own file does not
                        reach that far.

                        Set it to 0 to have 'scrollbind' mean scrolling
                        alone; each window then keeps its own page, as
                        two views otherwise do (|hexpair-two-views|).

                                                  *g:hexpair_short_commands*
g:hexpair_short_commands
                        Whether every command is also defined under a
                        short "HP" name - `:HPFind` for |:HexPairFind|,
                        :HPReplaceAllInPage for
                        |:HexPairReplaceAllInPage|, and so on for all of
                        them.  Default: 1. >

    let g:hexpair_short_commands = 0
<
                        Each short name is a one-line command that runs
                        the long one, so the arguments, the bang and the
                        completion come along and there is nothing for
                        the two to disagree about.  Set it to 0 if
                        commands of your own start with HP.

                                                       *g:hexpair_split_views*
g:hexpair_split_views   Whether a window that ends up showing a page a
                        SECOND time becomes an independent view of the
                        same file - its own buffer, its own page, its own
                        cursor - instead of a second window onto the same
                        buffer.  Default: 0. >

    let g:hexpair_split_views = 1
<
                        With it off, |:split| on a hex page means what
                        :split means everywhere else in Vim: two windows
                        onto one buffer, both showing the same page, and
                        turning the page in one turns it in the other.
                        That is the default because a page is thousands of
                        lines, and looking at two parts of ONE page in two
                        windows is a real use of a split.

                        With it on, |:split|, |:vsplit|, |:tab| |:split| -
                        any way a page ends up in a second window - give a
                        view of its own instead, opened on the same page
                        and the same byte, and a split of the text view
                        stays a text view.  Each such view is a buffer of
                        its own and stays in the buffer list until it is
                        wiped.

                        |:HexPairSplit| does the same thing explicitly
                        whatever this is set to, so the option is only
                        about what the PLAIN split commands do.

                        A view paged from piped input is never converted -
                        the temporary file it pages belongs to that buffer
                        - so a :split of one stays an ordinary split.

                                                             *g:hexpair_debug*
g:hexpair_debug         Trace every mapping between a cursor position and
                        a byte offset to |:messages|, for diagnosing a
                        cursor that landed on the wrong byte.  Default: 0. >

    let g:hexpair_debug = 1
<
                        Both directions are printed in the same terms, so
                        a page load, a jump to an offset and the byte a
                        write found can be read off against each other.

                                                          *HexPairStatus()*
HexPairStatus()         The view, the page and the byte under the cursor,
                        for 'statusline': >

    set statusline=%f\ %h%w%m%r\ %{HexPairStatus()}%=%l,%c%V\ %P
<
                        gives "hex 3/349 @0x50a01 (330241)" in a hex
                        page and "txt 3/349 @0x50a01 (330241)" in the
                        text view, and an EMPTY string in every buffer
                        hexpair has not touched - so one statusline
                        serves both.  The byte comes in both bases: hex
                        is what the dump's own offset column speaks and
                        the form |:HexPairGoOffset| and vimhex's @BYTE
                        take, decimal is what everything else does.

                        A cursor standing in the OFFSET column is on that
                        line's first byte - which is what the column
                        says.  Its digits are not payload and are not
                        counted as bytes, here or in |:HexPairInspect|.

                        A statusline function is called on every cursor
                        movement, so this one never walks the page: the
                        byte comes from the canonical layout.  On a page
                        with unwritten edits - marked with a "+" after
                        the page numbers - that is where the byte WAS,
                        since inserting or deleting hex digits above the
                        cursor moves what follows; |:HexPairPages| counts
                        the digits actually there and is the exact answer.

     *HexPairModified* *HexPairDiff* *HexPairFind-highlight*
                    *HexPairMark-highlight* *HexPairInspect-highlight*
The markings that are about bytes rather than about the cursor, with
their defaults: >

    highlight link HexPairModified DiffChange " edited, not yet written
    highlight link HexPairDiff     DiffAdd    " differs from |:HexPairDiff|'s file
    highlight link HexPairFind     Search     " a match of |:HexPairFind|
    highlight HexPairMark term=underline,bold cterm=underline,bold gui=underline,bold
    highlight link HexPairInspect  Visual     " what |:HexPairInspect| just read
<
The last one is |Visual| because that is what it means - a run of bytes
taken together, the way a selection is - and because it is the one stock
group the four above have not already taken.  It is transient: the run is
marked only while the cursor stays on the byte it was read from, so it
never has to share a byte with a marking that is about the bytes
themselves.

The fourth one is deliberately not a colour: a mark says "this place"
while the other three say "these bytes are different", underlining
coexists with a colour scheme instead of competing with it, and where a
mark lands on a byte that is also edited, differing or found, the
colouring wins - the markings do not blend, so one of them has to.

Linking rather than naming colours is what makes the markings look like
the rest of the editor: whatever your colour scheme does with a diff or a
search, hexpair does with these.  It is also why the first of them is
DiffChange and not the closer-sounding DiffText - Vim's own DiffText is
`guibg=Red` with no foreground at all, so on a light background it comes
out black on red, which is what this default used to be and no longer is.

What the three resolve to is worth knowing before overriding them.  With
no colour scheme at all Vim's own DiffChange, DiffAdd and Search set a
background and leave the foreground to |hl-Normal|, and Vim picks those
backgrounds to suit its own Normal - readable with 'background' either
way.  Every colour scheme shipped with Vim sets both.  So an override is
usually taste, not repair; where it IS repair, the scheme in question
makes |:diffthis| and 'hlsearch' just as hard to read, and that is the
thing to fix.

To see what yours does: >

    :highlight HexPairModified
    :verbose highlight DiffChange
<
An override wants a foreground AND a background, because giving one and
leaving the other to the scheme is how the two end up on top of each
other: >

    highlight HexPairModified ctermbg=224 ctermfg=88 guibg=#ffd7d7 guifg=#870000
    highlight HexPairDiff     ctermbg=194 ctermfg=22 guibg=#d7ffd7 guifg=#005f00
    highlight HexPairFind     ctermbg=229 ctermfg=94 guibg=#ffffaf guifg=#875f00
<
Those are light-background pastels, and the cterm numbers need a
256-colour terminal; on a dark scheme or an 8-colour terminal they are
the wrong answer, which is the other reason the defaults are links.

5. Filetype plugin                                          *hexpair-ftplugin*

The plugin bundles a filetype plugin (ftplugin/xxd.vim) with editing
defaults for xxd dumps.  It is sourced for every buffer with 'filetype'
set to xxd - which hexpair sets whenever the hex view is active - provided
filetype plugins are enabled (|:filetype-plugin-on|; any modern vimrc or
|defaults.vim| does this).  The defaults are buffer-local:

    'tabstop'       10   a <Tab> aligns past the offset column prefix
    'expandtab'          indent with spaces, never literal tabs
    'shiftwidth'    3    one shift = one hex byte (two digits + space)
    'formatoptions' ""   no automatic formatting
    'textwidth'     0    no automatic wrapping
    'autoindent'    off  no automatic indenting

Everything is reverted through |undo_ftplugin| when the hex view is
toggled off (also for buffers whose original filetype was empty, where no
|FileType| event fires and the plugin runs the undo itself).

To overrule the defaults (|ftplugin-overrule|): a personal
~/.vim/ftplugin/xxd.vim is sourced BEFORE the bundled file, so its
settings alone would be overwritten.  Either disable the bundled defaults
entirely by adding >
    let b:did_ftplugin = 1
<
to your ~/.vim/ftplugin/xxd.vim, or put individual overrides into
~/.vim/after/ftplugin/xxd.vim, which is sourced after the bundled file
and always has the last word.

The global 'paste' option is not part of the filetype plugin; it is
managed by the main plugin so it can be restored when the cursor leaves
the hex buffer - see |g:hexpair_paste|.

6. Writing in hex mode                                       *hexpair-writing*

Writing with |:w| while hex mode is active writes just the page you are
looking at, from either view - see |hexpair-paged-write| for the two
mechanisms and what each costs.  The file on disk always receives real
binary content, never the textual dump.

Before anything is written the page is validated (see the editing rules in
|hexpair-usage|): an invalid page aborts the write with an error, and both
the file on disk and the buffer keep their previous content.  So does a
banner line that was edited or removed in the windowed text view, where it
is what tells content and decoration apart.

The 'modified' flag reflects whether the buffer actually differs from
what is on disk, independently in each direction: entering hex mode with
unsaved changes already pending keeps the buffer marked modified, and
editing the dump (even if it was clean when hex mode was entered) marks
it modified when you toggle back - so |:q| without |:w| still warns, and
plain |:q| still refuses, exactly as it would in the normal view.

==============================================================================
7. Refreshing the dump                                        *hexpair-refresh*

Because the 'modified' flag correctly survives editing the dump without
writing (|hexpair-writing|), edits can accumulate across several
|:HexPairToggle| round trips without ever touching disk - and until the
next |:w|, the offset and ASCII columns of a bare or edited line stay
exactly as typed, not regenerated.

                                                            *:HexPairRefresh*
:HexPairRefresh         Regenerate the offset and ASCII columns from the
                        current hex payload, without writing to disk: the
                        same round trip a |:HexPairToggle| off followed by
                        on would perform, but staying in hex mode and
                        without the intervening write.  The cursor stays on
                        the same byte.

The dump is validated first, exactly as for |:w| (|hexpair-writing|): an
invalid dump refuses the refresh with an error, cursor parked on the
offender, and the dump keeps its previous (unrefreshed) content.

The 'modified' flag is unaffected by a refresh: a buffer that already
differed from disk still does afterwards, and one that did not still does
not - only the rendering changes, never a byte of the underlying content.

8. Paged large-file mode                                       *hexpair-paged*

Hex mode is always paged (|hexpair-states|); this section is about the
page machinery itself and about |:HexPairOpen|, the entry point that
never loads the file at all.

|:HexPairOpen| exists because |:HexPairToggle| needs a buffer, and getting
one means Vim reading the whole file first - which for a file too large to
load is exactly what you are trying to avoid.  :HexPairOpen reads only the
page it shows, so a file of any size opens instantly.

|:w| writes the page back - see |hexpair-paged-write| below.

                                                    *hexpair-windows-2gib*
On native Windows, files over 2 GiB are read and written through PowerShell
rather than xxd.  Everything works - reading, searching, comparing,
overwriting, growing, shrinking, |:w| {file} and |:saveas| - and what
changes is only how the bytes are moved and what that costs.  The limit is
outside this plugin, and is in two places at once:

- `xxd` carries its seek offset in a C `long` - strtol() into it, fseek()
  out of it - and a `long` is 32 bits on Windows, which is LLP64 (a 64-bit
  build widens pointers and `long long`, not `long`).  strtol() SATURATES
  rather than failing, so an offset past the limit silently becomes
  2147483647 and `xxd` reads from THERE.  `xxd -r`, which writes bytes at
  an offset, has the same limit.
- readblob(), the obvious fallback, has it too: read_blob() in Vim's
  blob.c declares a plain `struct stat` and calls plain fstat(), where the
  rest of Vim uses stat_T - `struct _stat64` on Windows, and vim.h says
  why.  st_size is a 32-bit _off_t in the plain one, so the computed
  length goes negative for a large file and read_blob() returns an empty
  blob AND success, with no error to catch.

Reading past the limit therefore goes through PowerShell, whose
FileStream.Seek takes an Int64 - an external tool this plugin otherwise
refuses to depend on, but a Windows-only one that Windows ships, and the
choice is against not reading the file at all.  Arguments go by environment
variable and the bytes come back through a temp file, so a path with a
space or a quote survives.

PowerShell does ONLY the seek: it writes the page's raw bytes to a temp
file, and xxd reads both the dump and the flat hex out of that, where there
is no seeking to do.  xxd's limit was never its formatting.  What is left
is one process start a page, a few hundred milliseconds; a file-wide scan
pays it per block.

Writing past the limit goes the same way.  `xxd -r` has the same 32-bit
offsets, so every step that moves bytes is PowerShell's: an overwrite
seeks and writes, a grow extends with SetLength and slides the tail along,
a shrink slides the tail back and cuts the file.  Each write reads back
what it wrote and refuses to call it done if the bytes are not there;
g:hexpair_verify_writes turns that check off.

SetLength INVERTS this plugin's own cost model, which is worth saying
plainly because it surprises: past 2 GiB on Windows the operation that is
most expensive everywhere else is the cheapest one here.  Neither Vim nor
xxd can shorten a file except by writing it afresh, so a shrinking write
copies the whole file on every other platform (|hexpair-paged-write|).
.NET truncates in place, so a 120 GiB file shrinks by moving the bytes
after the page and cutting the rest.  Growing is a tail slide rather than
a rewrite for the same reason, and both directions stay in place here
whatever the cost model would otherwise have picked.

`:w {file}` and `:saveas` work too: the three copies that build a saved
file - head, page, tail - go the same way, with the chunking INSIDE one
process, since that is the operation that walks a whole file.

                                                  *hexpair-windows-what-runs*
What runs where.  One rule: a range is xxd's only if xxd can reach ALL of
it, so every caller tests the END of what it is about to touch.  A range
that starts below 2 GiB and crosses it takes the slow path whole; checking
the start would hand xxd a range it can begin and not finish. >

  operation              elsewhere, and <2 GiB       past 2 GiB on Windows
  ---------------------  --------------------------  ---------------------
  read page/diff/search  xxd -s -l                   PowerShell seeks into
                                                     a temp; xxd reads that
  draw the page          xxd -g 1 -c N               same, offsets
                                                     renumbered in Vim
  overwrite, same size   xxd -r                      PowerShell, verified
                                                     by reading it back
  grow                   extend, slide tail, patch   SetLength, slide, patch
  shrink                 REWRITE THE WHOLE FILE      slide, SetLength - in
                                                     place
  :w {file}, :saveas     readblob + writefile        one process per range
<
Below 2 GiB nothing changes on any platform: xxd does what it always did.
Past it each operation costs one PowerShell start, a few hundred
milliseconds - a page turn is slower but usable, a file-wide scan pays it
per block and is slow.  Against that, the shrink row is this plugin being
FASTER on Windows than anywhere else.

                                                  *hexpair-windows-pwsh*
PowerShell is NOT used on Linux, macOS or the BSDs, and that is deliberate
rather than an omission.  PowerShell 7 (pwsh) runs there and the same
FileStream calls would behave identically - but there is nothing to fix: a
`long` is 64 bits on those platforms, so xxd seeks correctly and is faster
than starting a process per operation.  A pwsh path detected at runtime
would buy no correctness and cost a process start on every read.  This
fallback exists where xxd is BROKEN, not where another tool happens to be
available.

Linux, macOS and the BSDs are LP64: a `long` is 64 bits, so xxd's seek is,
and their struct stat.st_size is a 64-bit off_t, so readblob() would be
too.  WSL is a Linux build and has neither limit.  A 32-bit build of
anything shares the xxd half of this; hexpair does not detect that, being
gated on Windows.

Only a write that SHORTENS a file, `:w {file}`, and one that INSERTS
bytes with more than half the file after them need a Vim newer than the
plugin's usual baseline: patch 9.0.0795 with a 64-bit Number type
(+num64, standard on modern builds).  That is the patch that gave
readblob() an offset and a size; plain readblob(), which reads a whole
file and is no use here, is older.  It is checked when such a write is
attempted and refuses just that write, saying so.  Everything else -
viewing pages, navigating them, writes that keep a page's length, and
inserts with no more than half the file behind them - runs on Vim 8.0
like the rest of the plugin, needing nothing but `xxd`, and that is
tested rather than asserted: the regression suite is run against a Vim
8.0.0000 build on every push, where it passes in full, the checks for the
three operations above being replaced by checks that they are refused and
the file left alone.

Open a file directly in paged mode, without loading it as a normal
buffer first - straight from the command line: >

    vim -c 'HexPairOpen bigfile.bin'
<
or from within Vim:

                                                               *:HexPairOpen*
:HexPairOpen {file} [page]
                        Open {file} in paged mode, showing [page] (1-based,
                        default 1).  Does not read the rest of the file.
                        [page] takes the same three forms
                        |:HexPairPageGoto| does - a number, +N or -N, or $
                        for the last page - with a step counted from the
                        first page, which is where opening starts, so "+2"
                        is page 3.  An out-of-range or unparsable [page]
                        reports an error and leaves the current buffer
                        completely untouched - nothing is created.

                                                          *HexPairDiffWith()*
HexPairDiffWith({file})
                        Function form of |:HexPairDiff| {file}, for the
                        same reason |HexPairOpenFile()| exists: a name
                        with a space or a literal "$" does not survive
                        the Ex command line's own argument parsing.
                        `vimhexdiff` (|hexpair-vimhex|) calls it. >

                            call HexPairDiffWith($OTHER_FILE)
<
                                                          *HexPairOpenFile()*
HexPairOpenFile({file} [, {page}])
                        Function form of |:HexPairOpen|, for scripts,
                        mappings or shell wrappers that build the filename
                        programmatically (e.g. from an environment variable)
                        instead of typing it on the Ex command line.
                        Prefer this over constructing a |:HexPairOpen|
                        command-line string yourself when the name may
                        contain spaces or a literal "$" - :HexPairOpen's
                        `-nargs=+` argument parsing does not fully
                        round-trip fnameescape()'s escaping of such
                        characters, but a direct function call needs no
                        escaping at all: >
                            call HexPairOpenFile($MY_FILE)
<
          *:HexPairPageNext* *:HexPairPagePrev*
     *<Plug>(HexPairPageNext)* *<Plug>(HexPairPagePrev)*
:HexPairPageNext[!]     Show the next page.
:HexPairPagePrev[!]     Show the previous page.
                        Refuse to discard unsaved changes to the current
                        page without !.

                          *:HexPairPageGoto* *<Plug>(HexPairPageGoto)*
                                              *<Plug>(HexPairPageGotoForce)*
:HexPairPageGoto[!] {page}
                        Jump directly to {page}, which is one of:
                            {N}     the page numbered N, 1-based
                            +N, -N  N pages forward or back from this one
                            $       the last page
                            $-N     N pages back from the last one
                        `$-N` is the one a bare `-N` cannot express: that
                        counts from the page in view, this from the end of
                        the file.  `$+N` is refused where it is typed,
                        naming a page past the last one, which is never a
                        page.
                        A step past either end is refused with the same
                        "page N does not exist" as a number out of range,
                        rather than being clamped, so a mistyped step does
                        not quietly land somewhere else.  Refuses to
                        discard unsaved changes without !, same as above.
                        <Plug>(HexPairPageGoto) is the mapping equivalent:
                        it prompts with |input()| instead of needing a
                        typed {page}, and accepts the same forms.
                        <Plug>(HexPairPageGotoForce) is the same prompt but
                        discards unsaved changes without asking, like the
                        {page} variant with !.

                                                              *:HexPairPages*
:HexPairPages           Report the current page number, the total page
                        count, the absolute byte range shown and the byte
                        the cursor is on, e.g. "page 3 of 349, offsets
                        262145-393216 of total 45678901 bytes
                        (bigfile.bin); cursor on byte 0x50a01
                        (330241)".  The first half is what the page
                        banner shows (below), useful once the banner has
                        scrolled out of view; the second is a position in
                        exactly the form |:HexPairGoOffset| and vimhex's
                        @BYTE take, so where you are can be written down
                        and gone back to.

                        *:HexPairFind* *:HexPairFindText* *hexpair-find*
                            *:HexPairFindNext* *:HexPairFindPrev*
:HexPairFind[!] {bytes} Find {bytes} in the FILE, from the byte after the
                        cursor, and go there - turning the page if the
                        match is on another one.  |/| cannot do this: it
                        searches the page on screen, which is a window on
                        the file, and a sequence of bytes in a dump has
                        spaces, line breaks and an ASCII column through
                        the middle of it. >

                            :HexPairFind de ad be ef
                            :HexPairFind deadbeef
                            :HexPairFind de ?? be ef
<
                        A pattern is bytes, two hex digits each; spaces
                        between them are decoration, and a '?' stands for
                        any nibble.  A match starts on a byte, never
                        between two.  Every match on the page is marked
                        with |HexPairFind-highlight|.

                        The search obeys |'wrapscan'| like Vim's own, and
                        says when it wrapped.  ! forgets the pattern and
                        clears the marking - that is how a page stops
                        being covered in matches, and it has a mapping
                        target of its own, |<Plug>(HexPairFindClear)|; the
                        bare command says what is being looked for.

                        Only what is on SCREEN is marked, and it is
                        marked again as the window scrolls, so a pattern
                        that matches thousands of times on a page costs
                        no more than one that matches twice.

                        A match that straddles a page boundary is marked
                        on both pages it touches, each showing the bytes
                        it holds - the page's own bytes are searched with
                        a few of the neighbouring page's on either side,
                        since such a match fits whole inside neither.

                        What is searched is the file on disk.  Unwritten
                        edits are on the screen, where |/| and the eye can
                        find them.

:HexPairFindText {text} The same, for the bytes of {text}.
:HexPairFindNext        Repeat the last search forwards,
:HexPairFindPrev        or backwards.

                                    *:HexPairReplace* *:HexPairReplaceAllInPage*
:HexPairReplace {bytes} Put {bytes} in place of the match under the
                        cursor - which has to BE a match, or the command
                        would overwrite whatever the cursor happens to sit
                        on.
:HexPairReplaceAllInPage {pattern} / {bytes}
                        Put {bytes} in place of every match of {pattern}
                        on this page - the name says the scope, because
                        the scope is the surprising part: everything here
                        writes one page at a time, so a file-wide replace
                        would be a different mechanism with a different
                        failure to recover from, not a bigger version of
                        this one.  Step the pages to cover a file.  The
                        slash keeps the two arguments apart, which a
                        pattern of hex digits, spaces and '?' can never
                        contain. >

                            :HexPairReplaceAllInPage de ad be ef / 00 00 00 00
<
                        Both edit the PAGE, exactly as typing over the
                        dump would: the new bytes are marked as changed
                        (|HexPairModified|), one |u| takes the whole
                        replacement back, nothing reaches the file
                        until |:w| does, and a replacement of a different
                        length goes through the same length-changing
                        write - with the same question about what it will
                        cost - as any other insertion or deletion.

                        Both want the hex view: the text view has no hex
                        to replace.

       *:HexPairDiff* *:HexPairDiffShow* *:HexPairDiffNext* *:HexPairDiffPrev*
:HexPairDiff[!] [file]  Compare this view with [file]: every byte of the
                        page that differs from the same offset of [file]
                        is marked with |HexPairDiff|, and the command says
                        how many differ and where the first one is.  With
                        no argument it says what is being compared
                        against; with ! it stops comparing.

                        Comparing follows the pages: turning to another
                        page compares that one.  What is marked is what is
                        on SCREEN against the other file, so an edit shows
                        up at once - in the windowed text view as well as
                        in the dump (|hexpair-marking-views|).  The ! that
                        stops comparing also clears the marking, and has a
                        mapping target of its own:
                        |<Plug>(HexPairDiffClear)|.

:HexPairDiffShow        What the file being compared with holds HERE: the
                        byte under the cursor, or every byte of a Visual
                        selection, beside the bytes at the same offsets
                        over there.

                        The marking answers "which bytes differ" and stops
                        there.  This answers "what is over there instead",
                        and in particular says when there is NOTHING there
                        because that file ends before this offset - the
                        case a marking cannot express, since every byte of
                        such a page is marked and the reason is not on
                        screen.  Missing bytes are shown as `--`, so a byte
                        that is absent cannot be read as a byte that
                        happens to be 00.

                        The bytes reported are the page as it was READ,
                        not as the buffer now holds it, for the reason
                        |:HexPairDiff|'s counts are: this is about how the
                        two FILES compare, which unwritten edits are no
                        part of.  A long selection is summarised and the
                        listing stops after 32 bytes.
                        |<Plug>(HexPairDiffShow)| has a Normal-mode and a
                        Visual-mode form, `<Leader>D` in `hexpair.vimrc`.

                        Both views answer it, about the byte the cursor is
                        on in whichever one you are standing in.

:HexPairDiffNext        Go to the next CHANGE, or the previous one -
:HexPairDiffPrev        anywhere in the file, however many pages away.

                        A change is a run of bytes that differ, and these
                        move between changes rather than through the bytes
                        of one: where the files agree on byte 1, differ
                        over bytes 2-5, agree again over 6-8 and differ
                        from byte 9 on, |:HexPairDiffNext| from byte 1
                        goes to byte 2, from there to byte 9, and then
                        says there is no change after it - three presses
                        for two changes, whatever their length.

                        Backwards it goes to a change's FIRST byte too, so
                        from the middle of one it lands on that change's
                        own start, as |[c| does in a diff.

                        A difference past the end of THIS file (the other
                        one is longer) has nowhere to put the cursor, so
                        it is reported instead.

                        `vimhexdiff` (|hexpair-vimhex|) opens two files
                        side by side this way.

                                                        *hexpair-progress*
                        Both files are read a megabyte at a time, so
                        neither has to fit in memory - but on a large one
                        that takes long enough to look like a hang, so
                        from 16 MB up the scan says how far it has got: >

                          hexpair: comparing 2.3 GiB of 70.0 GiB (3%, CTRL-C stops)
<
                        and CTRL-C stops it, which answers with
                        "hexpair: stopped".  |:HexPairFind| and
                        |:HexPairFindNext| do the same; nothing has been
                        changed by the time either of them can be
                        interrupted, since both only read.

                                 *:HexPairModifiedNext* *:HexPairModifiedPrev*
:HexPairModifiedNext    Go to the next run of bytes edited and not yet
:HexPairModifiedPrev    written, or the previous one - the same idea as
                        |:HexPairDiffNext|, applied to your own changes
                        rather than to another file's.  Bytes that touch
                        are one edit, however they were typed, and the
                        cursor lands on the first byte of each; the
                        message says which of how many.

                        This one does not scan the file, and does not need
                        to: turning a page needs an unmodified buffer or a
                        bang that discards, so bytes edited and not yet
                        written only ever exist on the page in view.  Both
                        views walk their own - see |hexpair-marking-views|
                        for the one thing the text view cannot tell apart.

                                                     *:HexPairModifiedShow*
:HexPairModifiedShow    What was HERE before you edited it: the byte under
                        the cursor, or every byte of a Visual selection, as
                        the buffer holds it now beside what the page held
                        when it was read from disk.

                        |:HexPairDiffShow| against this view's own file
                        instead of another one, and the same two aligned
                        rows - `here` over `disk` - so the pair reads the
                        same way whichever asked.  The marking answers
                        "which bytes did I change" and covers the NEW byte,
                        so what the file has there is exactly what the
                        screen no longer shows; this is that byte.  An
                        untouched byte says so rather than refusing.

                        Bytes an INSERT has added are past the end of the
                        page as read, and there is nothing behind them yet:
                        they are shown as `--` and the heading says where
                        the page as read stopped.  A long selection is
                        summarised and the listing stops after 32 bytes.
                        |<Plug>(HexPairModifiedShow)| has a Normal-mode and
                        a Visual-mode form, `<Leader>d` in `hexpair.vimrc`
                        - the lowercase of the `<Leader>D` that asks the
                        same question of another file.

                        Both views answer it.  In the windowed text view it
                        inherits that view's one blind spot: a Vim string
                        holds no NUL, so a NUL and a line break read alike
                        there (|hexpair-marking-views|).  The hex view is
                        exact.

                        *:HexPairMark* *:HexPairGoMark* *:HexPairMarks*
                                                     *:HexPairMarkDelete*
:HexPairMark {name}     Remember the byte under the cursor as {name}.
:HexPairGoMark[!] {name}
                        Go back to it, turning the page if needed and
                        completing {name}.
:HexPairMarks           List the marks in this file, by position, with the
                        page each falls on.
:HexPairMarkDelete {name}
                        Drop one.

                        All four have a mapping target, and the three that
                        need a name ask for it - completing the names that
                        exist, the way |<Plug>(HexPairPageGoto)| asks for a
                        page: |<Plug>(HexPairMark)| to set one (typing a
                        name that exists is how a mark is MOVED to the byte
                        under the cursor), |<Plug>(HexPairMarkDelete)| to
                        drop one, |<Plug>(HexPairGoMark)| to go there and
                        |<Plug>(HexPairGoMarkForce)| to go there discarding
                        unwritten changes.  |<Plug>(HexPairMarks)| lists
                        them.  hexpair.vimrc puts all five under one
                        prefix (|hexpair-vimrc|).

                        Vim's own |mark|s are positions in a BUFFER, and a
                        paged buffer holds a different part of the file
                        from one page to the next, so a mark set on page 3
                        would mean something else on page 4.  These are
                        absolute byte offsets kept per FILE: every view of
                        that file shares them (|hexpair-two-views|), a
                        page turn cannot disturb them, and one left
                        pointing past the end - the file shrank under it -
                        is listed as such and refused on the jump.

                        A mark that falls on the page in view underlines
                        the byte it stands on, in both columns
                        (|HexPairMark-highlight|); |g:hexpair_show_marks|
                        turns that off.

                        They last as long as the Vim session does.

                          *:HexPairSplit* *:HexPairVSplit* *hexpair-two-views*
:HexPairSplit [page]    Open a SECOND view of the same file in a new
:HexPairVSplit [page]   window, showing [page] - by default the one this
                        view is showing, so the split starts as a copy and
                        is navigated from there.  [page] takes the same
                        forms as |:HexPairPageGoto| and is counted from
                        THIS view: `:HexPairSplit +1` puts the next page
                        beside this one, `:HexPairSplit $` the last.
                        :HexPairVSplit is the same thing in a vertical
                        split.

                        The two views share nothing but the file.  Each is
                        its own buffer with its own page, its own cursor
                        and its own unwritten changes, and a |:w| in either
                        patches only the page that view holds - so one can
                        be read while the other is edited, or bytes copied
                        from one region of a file into another.

                        The second buffer's name is the first's with a
                        number on it ("disk.img [hexpair page #2]"), which
                        is what tells them apart in |:ls|; the page banner
                        in both names the real file.

                        Writing one view does not lock the other out: what
                        a write checks is whether ITS OWN page changed on
                        disk, not whether the file did (see below).  Two
                        views of the SAME page are allowed, and then the
                        second write is refused, because that page really
                        did change under it - reload it with
                        |:HexPairPageGoto|! and redo the edit.

                        A view paged from piped input cannot be split: the
                        temporary file it pages belongs to that buffer and
                        goes when it does.  Save it with `:w {file}` first
                        and split that.

                        A plain |:split| is left alone by default - it
                        makes two windows onto one buffer, as it does
                        everywhere else in Vim.  |g:hexpair_split_views|
                        turns those into views of their own as well.

                                                        *:HexPairGoOffset*
:HexPairGoOffset[!] {byte}
                        Jump straight to a byte, decimal or 0x-prefixed,
                        turning the page it falls on if needed.  The
                        position is 1-BASED: byte 1 is the file's first
                        byte, the same numbering the page banner and
                        |:HexPairPages| use, so a number read off the
                        banner can be typed straight back in.  (The dump's
                        own offset column is `xxd`'s native 0-based
                        address and is left alone - the same split the
                        banner already makes.)  A hex number needs the
                        0x on it: a bare "ff" is not a byte position, and
                        says so.  `+N` and `-N` step from the byte the
                        cursor is on; `$` is the file's last byte and
                        `$-N` is N bytes back from it, which is the thing
                        a bare `-N` cannot say - that one counts from
                        wherever the cursor is, this one from the end.
                        `$-N` takes hex too (`$-0x10`).  `$+N` is refused
                        where it is typed: it names a byte past the last
                        one, which is never a byte.  |:HexPairPageGoto|
                        takes the same forms for pages, since the two
                        prompts sit under neighbouring keys and answering
                        one in the other's language should not be a
                        mistake.
                        Refuses to leave a page with unwritten
                        changes without !, like the other navigation
                        commands, and leaves you in whichever view you
                        were in.

As with |hexpair-usage|, no key mappings are defined by default; e.g.: >

    nmap <Leader>j <Plug>(HexPairPageNext)
    nmap <Leader>k <Plug>(HexPairPagePrev)
    nmap <Leader>g <Plug>(HexPairPageGoto)
<
Uppercase variants that discard unsaved changes without asking (like the
! commands) - Next/Prev need no <Plug> target for this, map the bang
command directly: >

    nnoremap <silent> <Leader>J :HexPairPageNext!<CR>
    nnoremap <silent> <Leader>K :HexPairPagePrev!<CR>
    nmap <Leader>G <Plug>(HexPairPageGotoForce)
<
Each page is bracketed by a leading and trailing banner line, e.g.: >

    " hexpair: page 3/349  bytes 262145-393216 of 45678901  bigfile.bin
    00040000: 41 42 43 44 45 46 47 48 ...                    ABCDEFGH...
    ...
    0005fff0: ...
    " hexpair: end of page 3/349
<
The banner's and |:HexPairPages|' byte range is 1-based and inclusive
(byte 1 is the file's first byte, so the LAST page's range always ends
exactly at the total) - unlike the hex dump's own offset column (e.g.
"00040000:" above), which is `xxd`'s native 0-based hex address and is
left alone.

A banner line - recognized as any line whose FIRST character is a double
quote - is purely decorative, exactly like the offset and ASCII columns
in the base mode (|hexpair-usage|): it is skipped entirely by cursor and
highlighting logic and contributes no bytes, so it can never be confused
with hex payload even though it contains ordinary decimal digits and
letters.  It is given a comment-like appearance via the |HexPairPageBanner|
highlight group (linked to the standard Comment group,
|highlight-groups|, by default - `xxd`'s bundled
syntax file defines no comment group of its own to reuse).

                                                    *HexPairPageBanner*
HexPairPageBanner       Highlight for the page banner lines.  Links to
                        Comment by default.

WRITING A PAGE                                        *hexpair-paged-write*

|:w| on a paged buffer writes just that page, by one of two mechanisms:

- The page still has the same LENGTH - you overwrote values, which is
  the common case.  The page is then patched IN PLACE: the file keeps
  its length and every byte outside the page keeps its content, without
  ever being read or written.  The cost is proportional to the page, not
  to the file, so it is the same on a 4 KiB file and a 400 GiB one.

- The page GREW - you inserted bytes.  Bytes cannot be spliced into the
  middle of a file, but they do not have to be: everything AFTER the
  insertion point has to move, and everything before it does not, and is
  not even read.  So the tail is moved right IN PLACE and the page
  patched in.  Appending to the last page moves nothing at all.  The
  temporary space needed is one block's worth of hex - a few tens of MB -
  whatever the size of the file; the tail is moved from the end backwards,
  so a byte is never overwritten before it has been copied, and no second
  copy of it is kept.
  (When the tail is more than half the file, moving it would cost more
  than rewriting it, so the case below is used instead.)

- The page SHRANK - you deleted bytes.  Moving the tail left is the same
  operation, but the file would then still be its old length with stale
  bytes at the end, and nothing in Vim or `xxd` can shorten a file
  except by writing it afresh.  So head, edited page and tail are copied
  through a temporary file, which then replaces the original; that needs
  temporary space the size of the whole file, and is the only operation
  that does.  If the copy back fails part way through, the temporary
  file holds the complete new content and its path is reported instead
  of being deleted.

Either change of LENGTH - the second case and the third - says by how much
the file will change, and how much of it has to be written, and asks for
confirmation first (|g:hexpair_page_confirm| turns the question off).  The
first case, the same-length patch, does not ask: it writes only the page.

Before any of them, the dump is validated exactly as in |hexpair-writing|,
and the page is checked for having changed underneath the view.  What
matters is not that the FILE changed but that THIS PAGE did, so the check
is made in two steps:

- the file's SIZE must be what it was: a different length moves every
  page after the change, so nothing about this page's offsets can be
  trusted any more;
- the page's own BYTES must be what they were, by a hash taken when the
  page was read and again now.

A change to the file that leaves both alone - another process rewriting a
different part of it, or a second view of the same file
(|hexpair-two-views|) writing its own page - is not a reason to refuse,
and is not refused.  A change to this page is, whatever the file's
modification time says about it: mtime has whole-second resolution, so a
writer that changes bytes in place within the same second is invisible to
it.  A refused write leaves the file untouched and the edit in the
buffer; reload with |:HexPairPageGoto|! and redo it.

Reading the page back costs what reading a page costs - hundredths of a
second, independent of the size of the file.  Where Vim has no |sha256()|
(a build without |+cryptv|) there is no hash to compare, and the
modification time is used instead - the weaker guard, and the one that
cannot tell a change to this page from a change to the rest of the file.

`:w {file}` means something different from a plain |:w|: not "patch this
page into its own file" but "save what I am looking at, as a whole, over
there".  It writes the ENTIRE content being paged, with this page's edits
in it, to {file}; the original is left exactly as it was.  For a view
paged from piped input this is the only way to save at all, and the view
adopts {file} afterwards, so a later plain |:w| patches pages into it -
the same way Vim's own `:w {file}` gives an unnamed buffer a name.

Because it copies the whole file, `:w {file}` needs readblob() -
|hexpair-paged|'s Vim requirement - and Vim's own refusal to overwrite an
existing file without a ! applies as usual.

                                                       *hexpair-saveas*
`:saveas {file}` is the other half of that pair, and means what it means
everywhere else in Vim: not "save a copy over there" but "this view edits
that file from now on".  The whole content is written to {file}, the view
adopts it, 'modified' is cleared, and a later plain |:w| patches pages
into {file} - while the file the view came from is left exactly as it
was.  `:file {name}` renames without writing anything, so the view goes on
editing its original file until the next write, which then adopts {name}
in the same way.

Inside the |BufWriteCmd| that does all of this, `:saveas` and `:w {file}`
look identical - <amatch> is the target for both.  What separates them is
that `:saveas` RENAMES THE BUFFER before writing it, so the buffer's own
name says which one this is.  That, and the fact that Vim leaves
'modified' to the autocommand for a 'buftype' of "acwrite", are what a
`:saveas` used to get wrong: the file was written, the flag stayed set,
and the view went on believing it edited the old file, so every write
after it copied the whole thing again instead of patching a page.

After a successful write the page is re-read from disk and the cursor
returns to the byte it was on, even when a splice moved every byte
behind it.  A shrinking write that empties the file entirely leaves a
view saying so, since there is then no page to show.

                                                     *g:hexpair_page_size*
g:hexpair_page_size     Bytes per page.  Default: 128 KiB (128 * 1024).
                        Must be a positive multiple of
                        |g:hexpair_bytes_per_line|; set it small (e.g. 512)
                        to work with small test files.  Changing it takes
                        effect on the next |:HexPairOpen| - an already-open
                        page keeps the size it was opened with. >
                            let g:hexpair_page_size = 4 * 1024 * 1024
<
                        A page is an ordinary Vim buffer, so everything
                        costs what that many lines cost: 128 KiB is 8192
                        lines, which loads in hundredths of a second and
                        writes in about a seventh of one, while 4 MiB
                        takes about three and a half seconds to write.
                        Since |:HexPairPageGoto| reaches any page
                        directly, a larger page buys nothing but that
                        wait.

                        There is a hard cap of 2147483647 bytes, and it
                        is a correctness boundary rather than a tidy
                        number: a page's length is handed to xxd's `-l`,
                        which is a C long and so 32-bit on Windows, and
                        to PowerShell as an [int], which is 32-bit
                        everywhere.  A larger page would overflow both
                        SILENTLY rather than fail.  Long before that it
                        is impractical anyway - a page is held as hex at
                        two characters a byte and drawn as dump lines at
                        nearly four, so a 2 GiB page wants some 8 GiB of
                        Vim.  The cap is where correctness ends.

                                                  *g:hexpair_page_confirm*
g:hexpair_page_confirm  Whether a write that changed the page's length
                        says what it will cost and asks first.  What it
                        costs differs: inserting bytes moves only what
                        follows them, deleting them rewrites the file
                        (see |hexpair-paged-write|).  A write that kept
                        the length patches just the page and never asks.
                        Default: 1.  Set to 0 to answer yes
                        automatically, e.g. in a script: >
                            let g:hexpair_page_confirm = 0
<
                                                             *hexpair-vimrc*
The set of mappings above ships with the plugin as hexpair.vimrc, next to
this help file, so that a vimrc can source it rather than copy it.  One
line, after 'mapleader' is set: >

    runtime pack/*/start/hexpair/hexpair.vimrc
<
That works on Linux, Windows and WSL alike, and names no directory of
yours: 'runtimepath' already points at the per-user Vim directory of the
platform - ~/.vim on Unix, ~/vimfiles on Windows - and |:runtime| searches
it.  An absolute `source ~/.vim/pack/...` would be wrong on Windows for
exactly that reason, even though Vim does expand `~` there.

The path is spelled out because a vimrc runs BEFORE packages are added to
'runtimepath' (|packload-two-steps|), so a bare `runtime hexpair.vimrc`
finds
nothing at that point.  With a plugin manager, whose directories are on
'runtimepath' by the time your vimrc reaches that line, the short form
works: >

    runtime hexpair.vimrc
<
The file never takes a key that is already mapped, so your own mappings
win - define them before that line.  It also carries every option and
highlight group as a commented-out example, and a note on adding
|HexPairStatus()| to 'statusline'.  Reading it is the fastest tour of
what there is to map.

                                                            *hexpair-vimhex*
A shell wrapper for opening a file - or piped input - straight in the hex
view ships with the plugin as hexpair.bashrc, next to this help file.
Source it from ~/.bashrc: >

    source ~/.vim/pack/plugins/start/hexpair/hexpair.bashrc
<
and it defines: >

    vimhex FILE          the first page
    vimhex FILE PAGE     that page, 1-based
    vimhex FILE @BYTE    the page holding that byte, cursor on it;
                         decimal or 0x-prefixed, and 1-based, so a
                         position |:HexPairPages| reported can be typed
                         straight back in
    vimhex - [...]       read from standard input instead of a file

    vimhex bigfile.bin
    vimhex bigfile.bin 3
    vimhex bigfile.bin @0x4a2000
    cat bigfile.bin | vimhex -
    dd if=/dev/sda bs=1M count=64 | vimhex - @1024
<
The same file also defines `vimhexdiff`: >

    vimhexdiff old.img new.img
<
which opens both files side by side, each marking the bytes that differ
from the other (|:HexPairDiff|), with the cursors on the first difference
and the two windows scroll-bound.  A jump in either window - a diff jump,
a search landing, |:HexPairGoOffset|, or a page turn made directly - takes
the other to the same byte (|g:hexpair_bind_pages|), so the two stay
together however far through the files you go.  Moving the cursor by hand
is the one movement that does not; |:HexPairSyncViews| is the way back
from it.

Set $VIMHEX_VIM to use a particular Vim.

                                                        *hexpair-vimhex-gui*
The same file defines `gvimhex` and `gvimhexdiff`, which are those two
commands again, taking the same arguments, with $VIMHEX_VIM defaulting to
`gvim` rather than `vim`: >

    gvimhex bigfile.bin
    gvimhexdiff old.img new.img
<
A $VIMHEX_VIM already set in the environment is left alone, so it still
names the Vim when you have pointed it at a particular gVim.  They
delegate to `vimhex` and `vimhexdiff` rather than repeating them, so all
four share one argument grammar.  cmd.exe gets the same four
(|hexpair-vimhex-windows|).

Three things in it are not incidental, and are commented in the file
itself so they survive being copied out of it:

- HexPairOpenFile(), not `-c 'HexPairOpen ...'`, for the reason given at
  |HexPairOpenFile()| above: a name with a space or a literal '$' does
  not survive the Ex command's own argument parsing, but the environment
  and a function call need no escaping at all.
- Everything runs from a |VimEnter| autocommand, because that is the only
  point that is after the content has arrived in BOTH cases: a plain -c
  runs after a named file has been read, but BEFORE standard input has.
- `-b` for the piped case.  Without it Vim may transcode the input on
  the way in, and unlike a named file there is nothing to re-read with
  ++bin afterwards (|hexpair-page-source|).  Save piped input with
  `:w {file}`; a plain |:w| has no file to write back to.

                                                    *hexpair-vimhex-windows*
The same two commands for cmd.exe ship beside it as vimhex.cmd and
vimhexdiff.cmd, taking the same arguments: >

    vimhex bigfile.bin
    vimhex bigfile.bin 3
    vimhex bigfile.bin $
    vimhex bigfile.bin $-5
    vimhex bigfile.bin @0x4a2000
    type bigfile.bin | vimhex -
    vimhexdiff old.img new.img
<
They need to be on $PATH, and the plugin's own directory is the tidiest
thing to put there, since updating the plugin then updates the commands:
`%USERPROFILE%\vimfiles\pack\plugins\start\hexpair`.  Add it through the
Environment Variables dialog rather than with `setx PATH "%PATH%;..."`,
which writes the system and user paths joined together into your user
Path and truncates the result at 1024 characters.

They default to the console `vim`; set $VIMHEX_VIM to `gvim`, or to a full
path, for another one.

gvimhex.cmd and gvimhexdiff.cmd are the same two commands again
(|hexpair-vimhex-gui| is the Bash pair), defaulting
$VIMHEX_VIM to `gvim` instead - for a double-click or a context-menu verb,
where there is no console for `vim` to run in and no way to pass
$VIMHEX_VIM.  They call vimhex.cmd/vimhexdiff.cmd rather than duplicating
their parsing, so keep all four files together.

vimhexdiff.cmd (and gvimhexdiff.cmd) takes two more forms, for the Explorer
context menu: >

    vimhexdiff /left FILE    select FILE as the left-hand side
    vimhexdiff /right FILE   select FILE as the right-hand side
<
Explorer runs a context-menu command once per selected file, each with its
own %1, so a verb cannot be handed two of them at once without a COM
handler; these are the two steps every diff tool on Windows solves that
with.  THE ORDER DOES NOT MATTER: each records its side in
%LOCALAPPDATA%\hexpair\diff-left.txt or diff-right.txt and stops there, and
whichever completes the pair opens the comparison and clears both, so the
next diff starts clean rather than reusing a stale selection.  Selecting
the same side twice overwrites it, which is not an error - and because
neither side has to come first, there is no "no left-hand file selected"
failure to report at all.

Both files are checked before the comparison opens - the one just clicked
as well as the one already remembered, since a file manager showing a
listing it has not refreshed will hand the entry a path that is no longer
there.  If one is missing the message names it by SIDE, left or right, and
clears only that selection; the other is kept, so nothing that is still
fine has to be selected again, and naming a new partner for it opens the
comparison straight away.

README.md, under "vimhex and vimhexdiff on Windows", has the registry
entries, and vimhex-contex-entry.add.reg/.remove.reg ship ready-made
versions of them, with nothing to edit for a default install: the paths
are written against
%USERPROFILE%\vimfiles\pack\plugins\start\hexpair.  Installed elsewhere?
Re-generate rather than edit: >

    python3 make-context-entry-reg.py "D:\your\path\hexpair"
<
Those two .reg files are generated because the values have to be
REG_EXPAND_SZ - the only registry string type whose %USERPROFILE% is
expanded when the shell reads it, where a plain REG_SZ would have the shell
look for a folder literally named that.  The .reg format writes that type
as hex(2): plus the string's UTF-16LE bytes, which is not something to
maintain by hand.  The expansion order is what makes it safe: the variable
is expanded at read time, %1 substituted afterwards, and once the variable
is consumed as a pair the only % left is %1's own.

The three entries live in ONE submenu rather than at the top level: >

    vimhex >  gvimhex this
              --------------------------
              gvimhexdiff select as left
              gvimhexdiff select as right
<
The folder is a verb carrying "ExtendedSubCommandsKey" and no \command of
its own, naming a key whose own \shell holds the children - the indirection
that keeps everything in HKEY_CURRENT_USER, where the older "SubCommands"
scheme would have needed HKLM and administrator rights.  Children are
ordered alphabetically by KEY name (hence the 10-/20-/30- prefixes) and the
separator is "CommandFlags"=dword:20 on the item below it.

Each entry also carries an "Icon", since Explorer cannot pull one out of a
.cmd file the way it can out of an .exe: icons/hexpair-open.ico, -pick.ico
and -with.ico, generated by icons/build.py from icons/design.py rather than
hand-drawn.  A V mark plus a "0x" badge on all three, and on the diff pair
a bigger badge of two coloured window panes standing in for which side
(left/right) that entry is - colour survives down to 16px where text or an
arrow stopped reading reliably.  Only the .ico files ship in the release
tarball.

                                                    *hexpair-vimhex-noconsole*
A console window flashes while the .cmd runs, and with a Windows Terminal
window already open it can attach to it and TAKE THE FOCUS from the file
manager the menu was invoked in.  That is accepted rather than worked
around, and the reasoning is worth keeping because the obvious fixes are
both worse: hiding the console needs either the Windows Script Host - whose
"run this command with a hidden window" is one of the shapes antivirus
heuristics look for, and which Microsoft is removing from Windows - or an
unsigned GUI stub .exe, which is usually worse for antivirus rather than
better.  A wscript.exe/.vbs launcher was built and then withdrawn for
exactly that reason.

Errors are still reported: the .cmd files check the exit status and print
what went wrong, then pause so it can be read.  $HEXPAIR_NO_PAUSE skips
that pause, for a caller that has its own way of showing the message.

vimhexdiff opens MAXIMIZED in gVim.  Two hex views side by side want the
full width, and a narrow window was also what made Vim stop for a hit-enter
prompt on each file it opened - a long path plus the size makes the file
message longer than one line, which is what triggers that prompt.  It sets
'shortmess' +=F to drop the message and maximizes with the Win32 GUI's own
`:simalt ~x`, guarded by has('gui_running') so console Vim is unaffected.

9. Limitations                                           *hexpair-limitations*

- A block device (/dev/sda) cannot be paged: the size the system reports
  for one is 0, and hexpair pages what a file says it holds, so it opens
  as an empty file with no pages.  Copy a slice of it into a file, or
  pipe one in - `dd if=/dev/sda bs=1M count=64 | vimhex -` - and page
  that (|hexpair-vimhex|).
- A page of a file this user cannot write opens |'readonly'|, so |:w|
  refuses it (E45) rather than converting the page and finding out from
  xxd.  |:w!| overrides that, as everywhere else in Vim, and then fails
  the way the file system makes it fail.
- The column arithmetic assumes the dump format produced by
  `xxd -g 1 -c N` (one-byte groups).  Do not re-filter the buffer with a
  different xxd invocation while hex mode is active.
- Undo does not cross a page boundary or a change of view, and is not
  meant to: turning a page, toggling between the hex and the text view and
  |:HexPairRefresh| each replace the whole buffer with |clear-undo| in
  effect, so |u| afterwards does nothing rather than putting bytes of a
  different page - or of the other rendering - into a buffer that claims
  to be this one, which a |:w| would then patch into the file at this
  page's offset.  Undo of edits made within one view of one page works
  normally.  What protects an edit you have not written yet is the refusal
  to turn a page or open another one while the buffer is |'modified'|,
  which is what |:HexPairPageNext|'s bang overrides.
- Cursor mapping is byte-exact for any byte the cursor can rest on.  A 0a
  byte acting as a line separator in the text view is the exception: the
  cursor cannot rest on it, so it clamps to the last byte of the line and
  a subsequent toggle lands there instead.  If the buffer was reloaded
  with ++bin and the file needed fileencoding transcoding, the position
  carried over the reload is a best-effort line/column match.
- A page is an ordinary Vim buffer, so it costs what that many lines cost,
  and a write costs a pass over them: about a seventh of a second for the
  default 128 KiB page, in proportion for a larger one
  (|g:hexpair_page_size|).  The size of the FILE never enters into it.
